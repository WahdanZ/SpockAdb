## Confirmed

| # | Question | Result | Plan impact |
|---|---|---|---|
| S1 | Can a second client use the VM Service through DDS while `flutter run` is attached? | **Yes.** `flutter run --machine` reports `app.debugPort` → `wsUri` `ws://127.0.0.1:<port>/<token>=/ws` on the **host**. The probe connected (protocol 4.15), listed the UI isolate and called extensions; `flutter run` kept working. | P4 connects through DDS whenever it can find the DDS URI [FR1]. |
| S2 | Which inspector entry point exists? | `ext.flutter.inspector.getRootWidgetSummaryTree` **yes**; `getRootWidgetTree` **no** on 3.22. | The inspector is out of scope for v1. What P4/P5 do gate on: `ext.flutter.inspector.trackRebuildDirtyWidgets` in `extensionRPCs` (rebuild storm, debug only) and `_flutter.getDisplayRefreshRate` answering (frame budget) [FR11]. |
| S3 | Are structured errors on? | **In this run, yes**: `structuredErrors` returned `enabled: "true"` (a JSON **string**) with no client having set it. But by source the default is `bool.fromEnvironment('flutter.inspector.structuredErrors', defaultValue: !kIsWeb)` inside an `assert`, so it is **debug only**; flutter_tools' DAP adapter passes `=false` for no-debug runs; an IDE may toggle it; and an app that replaces `FlutterError.onError` (Crashlytics, Sentry) never calls `FlutterError.presentError`, so there is no `Flutter.Error` and nothing in logcat beyond what its handler prints. | P4 never toggles it; it reads the state on connect and on `Flutter.ServiceExtensionStateChanged`. P5 falls back to logcat when it is off; Diagnose never says "no errors" from the absence of events [FR10]. Sample: *Custom FlutterError.onError* switch on the Errors screen. |
| S4 | Is HTTP profiling on by default? | **No**: `httpEnableTimelineLogging` returned `enabled: false` (a JSON **boolean**: dart:io answers booleans, Flutter's bool extensions answer `"true"`/`"false"` strings). `ext.dart.io.getHttpProfile` exists. By source: the flag is a per-isolate static, so hot restart resets it; only requests made after enabling are recorded; no event says when a client changes it; switching it off under DevTools breaks DevTools' Network page. | P4 enables it on connect and on each new UI isolate, re-reads it before each `getHttpProfile`, and on disconnect switches it off only if it was off at connect. Requests made before Spock connected are not captured — documented. Parse bool results of both shapes [FR10].  **Correction (P4a live check):** dart:io *does* post an `Extension` event `HttpTimelineLoggingStateChange` when logging is switched, so another client toggling it is visible. |
| S5 | How do services registered by `flutter run` (hot reload/restart) reach a second client? | `flutter run` registers `reloadSources`, `hotRestart`, `flutterVersion`, `compileExpression`, `flutterMemoryInfo` and `flutterGetSkSL` with DDS. A client learns them from `ServiceRegistered` events on the `Service` stream, which DDS replays on `streamListen(Service)`; each carries `service` and the `method` to call. The method name is an alias DDS hands out and recycles, so it is not stable across sessions or clients. | **Not in v1** (hot reload/restart are out of scope). If ever needed: map service → method from the latest `ServiceRegistered`, drop it on `ServiceUnregistered`, never hard-code a method name. |
| S6 | Which `Extension` events arrive with no interaction? | By source, DDS keeps up to 10 000 past events per stream for `Extension`, `Logging`, `Stdout` and `Stderr`, and replays them to every new `streamListen` client. The `Flutter.FrameworkInitialization` and `Flutter.FirstFrame` the first run saw were that replayed history, not live events. Live with no interaction: `Flutter.Frame` and, when a client changes an extension, `Flutter.ServiceExtensionStateChanged`. `Flutter.Frame` comes from `onReportTimings`: posted in engine batches, only for frames that were rendered, and its `startTime` is engine-monotonic µs, not wall-clock. The history also holds the `ServiceExtensionStateChanged` for `ext.flutter.connectedVmServiceUri` that flutter_tools caused by setting it to the **tokenised** URI (likewise `activeDevToolsServerAddress`), so a new client receives the token in an event [FR9]. The probe now splits counts at its connect time and never prints those two values; before/after counts are to be recorded in the S11 run. | `Flutter.Frame` is the frame source for P5 jank, placed by `startTime` on a monotonic offset. P4 dedupes events (timestamp + isolate + kind), marks events older than the connect time as history, and redacts event payloads. P5 does not rely on recovering errors from before connect: `Flutter.Frame` volume evicts them from the ring. The direct VM URI has no replay. |
| S7 | Do framework errors reach logcat in debug? | **Not while structured errors are on and the app keeps Flutter's `FlutterError.onError`** (seen in P0, `flutter run` from the CLI): overflow, `build()` and gesture errors go only to `Flutter.Error`. When structured errors are off (profile/release, `--dart-define=flutter.inspector.structuredErrors=false`, a no-debug DAP launch, an IDE toggle) `FlutterError.presentError` prints them (the first in full, later ones as `Another exception was thrown: …`) and they reach logcat. A replaced `FlutterError.onError` that never calls `presentError` sends them to neither. | Diagnose says so for debug builds (P1, done). P5 picks the source from the structured-errors state (S3). |
| S8 | Is an exception thrown in a platform channel handler a crash on Android? | **Depends on what is thrown.** Only a `RuntimeException` thrown synchronously in `onMethodCall` is caught by `MethodChannel`: it logs "Failed to handle method call" (tag `MethodChannel#…`), replies `PlatformException(error, …)`, the app survives (seen in P0). By source: a checked `Exception` (Kotlin throws one undeclared) reaches `DartMessenger.invokeHandler`, which logs "Uncaught exception in binary message listener" and replies empty, so Dart gets a `MissingPluginException` though the plugin exists; a `java.lang.Error` (Kotlin `TODO()` → `NotImplementedError`) is not caught and crashes the app. | P1's "plugin failure, not a crash" holds for the `RuntimeException` case. P5's classifier pairs a `MissingPluginException` with a preceding DartMessenger "Uncaught exception in binary message listener" line and reports a handler failure, not a missing plugin. Sample: `error_channel_checked`, `error_channel_todo` (device run: S21). |

| S12 | Can Spock find a running app through DTD, on a Flutter version that has the `ConnectedApp` service? | **Yes, on Flutter 3.47.5 / Dart 3.13.4** (Android 14 emulator, `flutter run --machine --print-dtd`):<br>• Every DTD writes a registry file `~/Library/Application Support/Dart/dtd/<pid>`: `{"wsUri", "epoch", "pid", "dartVersion", "workspaceRoot"}` — what `dart tooling-daemon --list` reads. No Dart SDK or IDE API is needed to find it.<br>• `flutter run` hosts its DTD inside the DDS process (the registry `pid` is `dart development-service`) and reports it as an `app.dtd` daemon event.<br>• `ConnectedApp.getVmServices` (no secret needed) returns the app's DDS `ws://…/ws` URI and a name `Kind: Flutter - Device: <device model> - Package: <pubspec name>`.<br>• Lifetime: after `flutter run` was interrupted, DDS (and its DTD) kept running and kept listing the app, which was still running on the device; no `VmServiceUnregistered` arrived. After DDS exited, its registry file **stayed behind** — `--list` skips it because the pid is gone. | P4b discovery: read the registry files → keep live pids → match `workspaceRoot` to the project → `getVmServices` → match the device by model name and the app by package. Treat the files as untrusted (the `wsUri` carries a secret: redact). Registration into the **IDE's** DTD is S22. |
| S9 | Is the **direct** device URI (logcat `Dart VM service is listening on …` + `adb forward`) refused while DDS owns the VM? | **No — redirected.** Checked on the Android 14 emulator with `flutter run` (3.22.2) attached: a client on the direct URI (device port 41111) connected and reported **DDS 1.6** — the VM hands it to DDS (host port 56810), so it gets DDS's view, history replay included. | While `flutter run` is attached, the logcat URI is as good as the DDS URI. Order B (S10: connecting directly *before* DDS starts, which can block `flutter attach`) is still open. |

## Notes for the gates

- Run device spikes with no Gradle build in parallel: an overloaded emulator drops `adb` and backgrounds the app, which looks like an app bug.
- P4's "pasted URI" path accepts and normalises every form a user can copy: `http://127.0.0.1:<port>/<token>=/` (`flutter run` console, logcat `Dart VM service is listening on …`), `ws://127.0.0.1:<port>/<token>=/ws` (`app.debugPort`), and DevTools links carrying `?uri=`. The token is redacted in all of them [FR9].
